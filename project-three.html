Project 03

AI Support Triage

A tool for the job I used to do at Santander UK. I handled first line support at Santander, taking 50+ calls and queries a day, so this is the thing I wished had been sitting next to me.

  • JavaScript
  • Node.js
  • Express.js
  • Claude API

Planned. This one is scheduled after the Takeaway Manager is finished. Nothing has been built yet, and this page describes what I intend to make.

Why this project

The slow part of first line support was never giving the customer the answer. It was everything before that: listening to the customer, working out exactly what the problem is, deciding how to fix it and then actually doing it.

This software can shave time off and allow colleagues to service more customers throughout the day. If the tool can figure out the correct plan of action based on the input, the colleague can just repeat the tool's suggestion and if not then the colleague can use the tool's reply as a starting off point.

What it will do

  • Sort by urgency ‐ so the queue arrives in the order it should be worked.
  • Categorise by type ‐ billing, access, technical fault, complaint.
  • Draft a suggested reply ‐ a starting point, not a finished answer.
  • Wait for a human ‐ every draft is approved or edited by a person before it goes anywhere.

How I'm building it

Same process as my other work: every requirement written as an issue with a definition of done, a branch and pull request per feature, and tests running automatically before anything merges.

The new part is calling a language model from my own code rather than using one as a tool while I work. That means the model call lives on a server I control, not in the browser, because the API key has to stay private.

Decisions made up front

Nothing sends by itself. The model drafts, a person approves. A tool that emails customers automatically is a tool that can embarrass you automatically, and in a support setting that matters more than the time it saves.

The API key never enters the repository. It lives in an environment variable locally and in the host's secret storage when deployed, with the .env file listed in .gitignore from the very first commit.
